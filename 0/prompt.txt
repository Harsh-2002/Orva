**Adopt a hybrid of candidate #1: reimplement detection/download/verify inline in `upgrade.go` (which is already ~80% custom), but do NOT hand-roll the binary swap — reuse `github.com/creativeprojects/go-selfupdate/update.Apply`.** Drop every symbol you currently use from the top-level `selfupdate` package. ### Why this is the right risk/benefit call

The load-bearing fact I verified: **openpgp is imported by exactly one file** — `go-selfupdate/validate.go`, which lives in the top-level `selfupdate` package (the `PGPValidator` type). The `update` and `internal` subpackages import **neither** the parent package nor openpgp (confirmed: `update/*.go` imports only `.../internal` + stdlib crypto; `internal/*` imports only stdlib + `x/sys/windows`, already an Orva dep).

govulncheck flags GO-2026-5932 at the **import/package** level (it's an "unmaintained, unsafe by design" advisory, not a specific vulnerable symbol), so it fires as long as any *reachable* package imports `x/crypto/openpgp`. That's why bumping can't help — v1.6.0 imports it unconditionally, no build tags. But package reachability is per-package: if Orva imports only `go-selfupdate/update` and never the parent `selfupdate` package, **openpgp leaves the reachable graph** and the finding disappears. `go mod why golang.org/x/crypto/openpgp` should then report "main module does not need package," and `go-github` / `ulikunitz/xz` get pruned as bonus.

Weighing the alternatives honestly:
- **#2 (fork with PGP build-tagged out):** dominated. You'd own a 30+ file fork forever, rebasing upstream, to use ~5% of it — and you'd still depend on the same maintenance-risk you're trying to escape. Vendoring only the `update` package (the 1b fallback below) achieves the same isolation without a fork.
- **#3 (accept + suppress):** low effort but the wrong terminal state. govulncheck has no native ignore file — you'd have to introduce osv-scanner + a config or grep-filter the ID in CI (neither exists today; there is currently no govulncheck wiring at all). It hides the ID globally (could mask a *real* future x/crypto/openpgp CVE), ships an admittedly-unmaintained crypto package in every binary, and re-surfaces on every audit. Reasonable only as a time-boxed stopgap if a release must ship before the code lands.
- **Fully hand-rolled swap (naive #1):** the trap. Reimplementing the Windows atomic replace (`SetFileAttributesW` hide dance, "close before rename or Windows says file-in-use", rollback-on-failure) is exactly the code you do NOT want to rewrite for a *low-severity, dead-code* advisory. Reuse it.

The severity here is effectively zero (dead code — Orva only ever instantiates `ChecksumValidator`, pure SHA-256), so the correct posture is the **minimum-risk path that still yields a clean scan**. Reusing `update.Apply` is that path.

Replace each parent-package symbol currently used:

1. **`selfupdate.NewGitHubSource`/`NewUpdater`/`DetectLatest` → a small `detectLatest(ctx, repo)`** that does `GET {githubAPIBase}/repos/{owner}/{repo}/releases/latest`, decodes `tag_name` + `assets[]{name,browser_download_url}`. Resolve the asset deterministically by **exact name** `orva-cli-&lt;goos&gt;-&lt;goarch&gt;[.exe]` (this is *stronger* than the old `^orva-cli-…` regex — it fully eliminates the wrong-OS "exec format error" class the filter was patched for) and grab the `checksums.txt` asset URL. This mirrors `scripts/install.sh::resolve_version` exactly.

2. **`selfupdate.ParseSlug`** → `strings.SplitN(orvaRepo, "/", 2)`.

3. **`*selfupdate.Release` + `.Version()`/`.LessOrEqual()`/`.ValidationAssetURL`/`.AssetName`** → a local `type releaseInfo struct { Tag, AssetName, AssetURL, ChecksumsURL string }`. Version comparison: reuse the library's exact semantics — extract `\d+\.\d+\.\d+` from the tag, `semver.NewVersion`, compare. 4. **`selfupdate.ExecutablePath()`** → `os.Executable()` then `filepath.EvalSymlinks()`. This is **critical and must not be skipped**: bare-metal installs symlink `/usr/local/bin/orva → /opt/orva/bin/orva` (see `install.sh::install_cli_shortcut`), and you must replace the real target, not overwrite the symlink with a file.

5. **`updater.UpdateTo` → download + verify + apply**, replacing go-selfupdate's `download → ChecksumValidator → decompressAndUpdate` chain (Orva ships raw uncompressed binaries, so the decompress step was already a passthrough):

   - **`update.Apply(bytes.NewReader(data), update.Options{TargetPath: exe})`** — TargetMode defaults to 0755; empty `OldSavePath` removes the `.old` on Unix and hides it on Windows. Optionally also pass `Options.Checksum: sha[:]` for belt-and-suspenders re-verification immediately before the swap.

## Honest risks and mitigations

1. **Reachability assumption is the whole thesis.** If anything under `update`/`internal` transitively pulled the parent package, openpgp would remain. Verified it does not. Mitigation: the `go mod why` + govulncheck check above is the fast, definitive gate — run it before merging.
2. **Windows atomic replace** — highest consequence. Mitigation: *unchanged* — you reuse `update.Apply`. Zero new risk vs today. This is the single strongest reason to prefer this over a from-scratch rewrite.
3. **Symlink clobbering on bare-metal.** Mitigation: `EvalSymlinks` before `Apply` (item 4 above) + the symlink unit test.
4. **GitHub API auth/rate limits.** The old path used go-github + `GITHUB_TOKEN`; unauthenticated is 60/hr/IP (fine for a human upgrade, and `install.sh` already relies on it). Mitigation: honor `GITHUB_TOKEN`/`GH_TOKEN`, send a `User-Agent`, and surface a clear message on HTTP 403 rate-limit. `upgrade-test.sh` already threads the token through.
5. **Asset-download redirects.** Mitigation: use the default client (follows redirects, strips cross-host `Authorization`); attach the token only to the API call, never to the pre-signed asset GET — exactly what `install.sh` does.
6. **`go mod tidy` pruning.** Mitigation: promote `Masterminds/semver/v3` to a direct require (still used for version compare); verify `make cli` + `make cli-all` build after tidy.
7. **Supply-chain: still depends on the module.** Mitigation: acceptable (advisory is about openpgp, not go-selfupdate). If unacceptable long-term, escalate to fallback 1b (vendor `update`).
