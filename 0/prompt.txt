## Methodology

Own instance on :18544, `make build`, tmpdir with a `rootfs` symlink. Probe target = a listener on the daemon's control-plane address on a fresh port, so a connect walks the *entire* rule vector (the control-plane allow has a `dport` that doesn't match, so evaluation continues) and lands on NSTUN's default-ALLOW. Timing is `process.hrtime.bigint()` around `net.connect` inside the handler, hundreds of samples per invocation.

Steady-state warm workers: after each rule-count change I drain the pool with a `PUT memory_mb` (the trick `egress-test.sh` uses — the 60 s policy-recycle rate limit doesn't apply), then run a throwaway invocation, then measure. Each measured worker's generation is confirmed by reading `--config` out of the live nsjail argv and matching it against `/firewall/status.policy_generation` (printed as `gen_in_worker=True` on every row). Levels are visited in a rotated order each round so drift can't align with the ladder.

Two independent estimators of scan cost: the **allow path** (matches nothing → full walk), and **reject depth** — inside one policy, compare a destination matched by the *first* reject rule (`169.254.169.254`, position 8) against one matched by the *last* (`198.18.3.99`, position 1007). Same worker, same policy; only walk depth differs.

Two false starts, both corrected: my first probe listener held connections open and never read, which I initially misread as nstun slowness — it was actually the Q2 flow-cap effect leaking into the Q1 rig. Q1 now runs against a server that closes on accept (flow map stays empty).

**Verdict: noise.** 1000 rules add ~5 µs to a connect that costs ≥100 µs on the fastest possible path and 10–100 ms to any real internet destination — 0.005–0.05%. You'd need ~200,000 rules to add 1 ms. The nftables set-lookup → NSTUN linear-scan change is not a measurable regression at any blocklist size an operator would plausibly enter. ## Q2 — the flow cap

The concern is **confirmed at the mechanism level**, reproduced both through Orva and by driving nsjail directly with the published policy generation.

- **Cap is exactly 1024 TCP flows per nsjail process** (per warm worker — the log line is tagged with the nsjail pid/tid). Flooding held precisely 1024; the 1025th onward produced `[W] handle_tcp4():822 Maximum number of TCP flows (1024) reached, dropping`, once per dropped SYN.
- **At the cap a REJECT rule stops failing fast.** `169.254.169.254` (a shipped `default` reject) answers `ECONNREFUSED` in **0.9–4.4 ms** below the cap, and at the cap returns **nothing at all** — 2 s, 3 s and 6 s probe timeouts all expired with no RST. A fresh *allowed* connection behaves identically. From inside the guest, blocked and allowed are indistinguishable: everything just hangs. With no application timeout the guest would wait out the kernel's SYN retries (~130 s).
- **The fd limit is not a defence.** Orva doesn't pass `--rlimit_nofile`, so the guest inherits nsjail's default of 32 (`Max open files 32 32`); a Node handler gets **14 concurrent sockets before EMFILE**. But saturation needs only *one* fd at a time: a plain sequential loop of connect → close, against a peer that doesn't close first, saturated after exactly **1025 connections in 2.4 s** (2.5 s / 3.7 s / 25.6 s across runs). That is well within one warm worker's lifetime.
- **Who closes first decides everything.** Against a server that closes on accept, 2000 sequential connects completed in 3.1 s with zero drops and flat latency across all 20 bins — flows are freed immediately. Against a peer that never closes, the map fills and stays full.
- **Recovery is slow but automatic.** After saturation, a blocked destination stayed unanswered for 40–56 s of complete idle before flipping back to `ECONNREFUSED` (55 s and 56 s in the two scripted runs). Releasing 200 held sockets produced no relief within 200 ms; under continued churn ~8% of connects stall ~2 s.
- **Not a regression from this branch.** `origin/main` already spawned egress sandboxes with `--user_net` (NSTUN), so the 1024 cap and the drop-at-cap behaviour predate the nftables removal. What changed is only *where* the REJECT decision lives — and on either implementation the SYN never reached the deciding layer once the cap was hit.

**Verdict: real, but bounded and not caused by the blocklist.** It is a genuine gap between documented behaviour (`ECONNREFUSED` for blocked destinations) and behaviour under saturation, reachable by a single-threaded function doing &gt;1024 short-lived outbound connections to keep-alive-style peers inside ~55 s. It self-heals, it is per-worker (one function can't wedge another), and it is unaffected by blocklist size since the cap is checked before policy evaluation. My recommendation is documentation plus, if anything, per-worker connection-churn observability — raising `--rlimit_nofile` would make it *easier* to hit, not harder.
