## Methodology

Own instance on :18544, `make build`, tmpdir with a `rootfs` symlink. Probe target = a listener on the daemon's control-plane address on a fresh port, so a connect walks the *entire* rule vector (the control-plane allow has a `dport` that doesn't match, so evaluation continues) and lands on NSTUN's default-ALLOW. Timing is `process.hrtime.bigint()` around `net.connect` inside the handler, hundreds of samples per invocation.

Steady-state warm workers: after each rule-count change I drain the pool with a `PUT memory_mb` (the trick `egress-test.sh` uses — the 60 s policy-recycle rate limit doesn't apply), then run a throwaway invocation, then measure. Each measured worker's generation is confirmed by reading `--config` out of the live nsjail argv and matching it against `/firewall/status.policy_generation` (printed as `gen_in_worker=True` on every row). Levels are visited in a rotated order each round so drift can't align with the ladder.

Two independent estimators of scan cost: the **allow path** (matches nothing → full walk), and **reject depth** — inside one policy, compare a destination matched by the *first* reject rule (`169.254.169.254`, position 8) against one matched by the *last* (`198.18.3.99`, position 1007). Same worker, same policy; only walk depth differs.

Two false starts, both corrected: my first probe listener held connections open and never read, which I initially misread as nstun slowness — it was actually the Q2 flow-cap effect leaking into the Q1 rig. Q1 now runs against a server that closes on accept (flow map stays empty).

**Per-rule cost ≈ 5 ns.** Both estimators agree: walking 999 extra rules costs ~5 µs (reject-depth: 0.095 → 0.100 ms; allow path: 0.101 → 0.106 ms). p50/p95 wander by ±0.1 ms with no ordering by rule count — the 50-rule row is often the slowest.

**Verdict: noise.** 1000 rules add ~5 µs to a connect that costs ≥100 µs on the fastest possible path and 10–100 ms to any real internet destination — 0.005–0.05%. You'd need ~200,000 rules to add 1 ms. The nftables set-lookup → NSTUN linear-scan change is not a measurable regression at any blocklist size an operator would plausibly enter. ## Q2 — the flow cap

The concern is **confirmed at the mechanism level**, reproduced both through Orva and by driving nsjail directly with the published policy generation.

- **Cap is exactly 1024 TCP flows per nsjail process** (per warm worker — the log line is tagged with the nsjail pid/tid). Flooding held precisely 1024; the 1025th onward produced `[W] handle_tcp4():822 Maximum number of TCP flows (1024) reached, dropping`, once per dropped SYN.
- **At the cap a REJECT rule stops failing fast.** `169.254.169.254` (a shipped `default` reject) answers `ECONNREFUSED` in **0.9–4.4 ms** below the cap, and at the cap returns **nothing at all** — 2 s, 3 s and 6 s probe timeouts all expired with no RST. A fresh *allowed* connection behaves identically. From inside the guest, blocked and allowed are indistinguishable: everything just hangs. With no application timeout the guest would wait out the kernel's SYN retries (~130 s).
- **The fd limit is not a defence.** Orva doesn't pass `--rlimit_nofile`, so the guest inherits nsjail's default of 32 (`Max open files 32 32`); a Node handler gets **14 concurrent sockets before EMFILE**. But saturation needs only *one* fd at a time: a plain sequential loop of connect → close, against a peer that doesn't close first, saturated after exactly **1025 connections in 2.4 s** (2.5 s / 3.7 s / 25.6 s across runs). That is well within one warm worker's lifetime.
- **Who closes first decides everything.** Against a server that closes on accept, 2000 sequential connects completed in 3.1 s with zero drops and flat latency across all 20 bins — flows are freed immediately. Against a peer that never closes, the map fills and stays full.
- **Recovery is slow but automatic.** After saturation, a blocked destination stayed unanswered for 40–56 s of complete idle before flipping back to `ECONNREFUSED` (55 s and 56 s in the two scripted runs). Releasing 200 held sockets produced no relief within 200 ms; under continued churn ~8% of connects stall ~2 s.
- **Not a regression from this branch.** `origin/main` already spawned egress sandboxes with `--user_net` (NSTUN), so the 1024 cap and the drop-at-cap behaviour predate the nftables removal. What changed is only *where* the REJECT decision lives — and on either implementation the SYN never reached the deciding layer once the cap was hit.

**Verdict: real, but bounded and not caused by the blocklist.** It is a genuine gap between documented behaviour (`ECONNREFUSED` for blocked destinations) and behaviour under saturation, reachable by a single-threaded function doing &gt;1024 short-lived outbound connections to keep-alive-style peers inside ~55 s. It self-heals, it is per-worker (one function can't wedge another), and it is unaffected by blocklist size since the cap is checked before policy evaluation. My recommendation is documentation plus, if anything, per-worker connection-churn observability — raising `--rlimit_nofile` would make it *easier* to hit, not harder.

# Build cache: recommendation

**Recommendation: Option B — a per-function cache — implemented as a *separate* persistent mount so only the two package caches persist, not `HOME`. Do it in two phases; phase 0 is a bug fix you want regardless. Reject C and D outright. ## 1. What the code actually does (evidence)

- Jail mounts: `-B &lt;codeDir&gt;:/code` (**read-write**) and `-B &lt;scratch&gt;:/tmp` — `backend/internal/sandbox/build.go:215-216`. The chroot itself is the runtime rootfs and is **read-only** (no `--rw` anywhere in `backend/internal/sandbox/`).
- `HOME=/tmp/home`, `TMPDIR=/tmp`, fixed `PATH` — `build.go:252-256`. `buildHomeDir = buildTmpDir + "/home"` (`build.go:44`), i.e. HOME is inside the one throwaway mount.
- The scratch dir is created per build under `&lt;dataDir&gt;/build-tmp` (`builder.go:548-551`), `chmod 0777` (`build.go:142`), and **`defer os.RemoveAll(scratch)`** (`build.go:138`). That single line is the whole regression: npm's cacache and pip's `http-v2` live there and are deleted at the end of every build.
- Env forwarded from orvad: `NPM_CONFIG_*`, `npm_config_*`, `PIP_*`, plus the six proxy vars — `builder.go:580-585`, applied in `withRegistryEnv` (`builder.go:589-617`), and caller env overrides the structural env (`build.go:257-262`).
- Concurrency: `NumCPU` workers, 64-deep channel (`queue.go:71-79`). Builds of the *same* function are serialised by `FnLock` (`queue.go:158-162`), wired in production at `server.go:204`. Different functions build concurrently.
- Already-free case: identical tarball hash short-circuits the whole install (`builder.go:135-145`). So the cache only matters when **code changed but dependencies did not** — which is precisely the iteration loop.
- `flock`, `rename`, `renameat2`, `link`/`linkat` are all in the build seccomp set (`seccomp.go:35-37`, `seccomp.go:119-125`), so no seccomp work is needed for either cache.

## 2. Threat model, plainly

The only actor who can influence a build is someone who can deploy — i.e. the operator or a credential holder, so this is not a multi-tenant build farm. The realistic attacker is a **malicious or compromised npm package in function A's transitive dependency tree**, whose `postinstall` script runs as arbitrary code inside A's build jail. The question is therefore not "can tenants attack each other" but "when one function's dependency tree goes bad, does it stay contained to that function, or does it get to write into something function B reads" — and lateral movement to a function that never depended on the bad package is a real escalation worth one cheap design decision, but not worth an architecture.

Two asymmetries matter. **Only node builds contain an attacker.** Orva runs pip with `--only-binary=:all:` (`builder.go:489`), so no `setup.py` executes and the python build jail contains nothing but pip itself. And isolation between builds today is by **bind mount, not by uid** — every jail runs as the same host uid; the only reason A cannot touch B is that B's directory is not mounted. A shared cache would be the *first and only* writable surface two mutually distrusting builds share.

## 3. The crux — and your premise is wrong

You wrote that npm's cache is content-addressed and integrity-verified, so a poisoned entry would simply miss. That is true of the *content store* and false of the *cache as a whole*. I tested both installers on this box rather than reasoning about it.

**npm, content tampering — your model holds.** I appended junk to every blob under `_cacache/content-v2/`. npm detected it, printed `cached data ... seems to be corrupted. Refreshing cache`, refetched, and installed clean bytes. Poisoned content at an authentic integrity path is a SHA-512 second preimage; that door is shut.

**npm, metadata forgery — your model breaks.** The packument is cached *in the same cacache*, keyed by URL, and its index entry is `sha1(entry)\t{json}` (`cacache/lib/entry-index.js:134,257,295-307`) — an unkeyed corruption checksum, forgeable by anyone who can write the directory. I forged a `dayjs@1.11.11` packument whose `dist.integrity` matched a poisoned tarball I placed in the content store. Result:

```
added 1 package in 349ms
module.exports = "MALICIOUS_PAYLOAD";
```

That was a **default `npm install`** — no `--prefer-offline` — because the attacker also controls the cached `resHeaders`, so I set `cache-control: public, immutable, max-age=31557600` and npm never revalidated. The victim's freshly generated `package-lock.json` recorded the *poisoned* integrity as truth. Content-addressing does not help when the trust anchor lives in the same attacker-writable store.

The one real defence: with an **authentic `package-lock.json` already in the tarball**, the same poisoned cache was rejected and npm installed genuine dayjs. So npm is safe only for users who commit a lockfile — which Orva neither requires nor checks.

**pip — worse, and pip says so itself.** The cache is `sha224(url)` → `&lt;path&gt;` + `&lt;path&gt;.body` (`SafeFileCache._get_cache_path`, `pip/_internal/network/cache.py:62-68`), with **no content verification on read**. Poisoning only the wheel body fails loudly, because `req.hashes(trust_internet=True)` (`prepare.py:338-368`) supplies the `sha256` from the simple index. But the index response is in the same URL-keyed cache. I patched the index JSON's `sha256` to match a poisoned `idna` wheel:

```
Successfully installed idna-3.7
MALICIOUS_PIP_PAYLOAD = True
```

No warning. And there is no lockfile escape hatch in practice — `requirements.txt` carries hashes only if the user writes `--hash=` lines, and Orva does not pass `--require-hashes`. pip's own docstring states the assumption a hostile writer breaks: *"we assume that the server will only ever return the same data for the same URL"* (`cache.py:43-55`). Its cache metadata is `cc=4,` + msgpack of the response headers — trivially rewritten to extend freshness to a year.

**Conclusion: a shared read-write cache is a genuine arbitrary-code-execution channel from any node build into every later build of any language.** Not a theoretical poisoning surface — a demonstrated one, in under an hour, with default flags.

## 5. Why the alternatives lose

- **A (status quo).** Gives up nothing; costs ~4 s (fast link) to ~15 s (slow link) per node deploy, forever, on the most common developer action. Defensible, and I would accept it — but note you are *already paying the disk write*: npm fills 46 MB of cache inside the scratch dir on the data-dir filesystem and then deletes it. Keeping it is nearly free in I/O; you are throwing away work you already did.
- **C (shared RW).** Buys cross-function reuse on first deploys. Gives up containment entirely — see §3. Reject.
- **D (shared RO + writer).** Asymmetric and doesn't work: pip tolerates a read-only cache (writes are swallowed by `suppressed_cache_errors`, `cache.py:28-36`), npm does not — cacache write failures are fatal, and there is no read-only mode. Making it work needs a per-build overlay, which needs mount privileges the daemon does not have, or an out-of-band warmer that must itself resolve every function's dependency graph. High complexity, and the warmer becomes a new trusted component. Reject.
- **E (registry proxy / verdaccio / devpi).** This is the *architecturally correct* answer — the cache lives in a process nobody else can write, and it would also cut registry flows. It is also a whole new daemon, with HTTPS interception or a rewritten registry URL that breaks lockfile `resolved` fields, plus egress-policy interaction. Wildly disproportionate for a single-operator homelab FaaS. Correct answer if Orva ever becomes multi-tenant; wrong answer today.
- **E-variant (seed `node_modules` from the previous version dir).** Faster than a package cache in principle, but a hardlinked or copied tree that npm then mutates in place is a correctness hazard, and copying 43–171 MB can cost more than the download saved. Not worth the risk.
- **B (per-function).** Buys ~55% of node deploy time and ~18% of pip deploy time on exactly the workflow that matters (edit code → redeploy, deps unchanged). Gives up **nothing across functions**: `&lt;dataDir&gt;/build-cache/&lt;fnID&gt;/` is written and read only by builds of that function, and `FnLock` (`queue.go:158-162`) already serialises those, so there is no concurrent-writer question at all. The only residual property given up is *persistence within one function*: a dependency that poisoned function A's cache survives A's author removing the dependency. That is real and needs a purge control, but it is bounded to a function that was already compromised.

## 6. Implementation sketch

**Phase 0 (do regardless, ~30 lines, no security question):**

1. In `buildJailArgs`, set `npm_config_cache`, `npm_config_logs_dir`, and `PIP_CACHE_DIR` explicitly, *after* the forwarded env wins today. Right now an operator with `npm_config_cache=/root/.npm` in orvad's environment has that forwarded (`builder.go:580`) into a jail where the chroot is read-only and the path is unmounted — builds break with a confusing EROFS. Orva must own these three variables.
2. Sweep stale `&lt;dataDir&gt;/build-tmp/build-*` on boot. `defer os.RemoveAll` (`build.go:138`) only covers a live process; a crash leaks tens of MB per in-flight build, permanently.

**Phase 1 (the cache):**

- Directory: `&lt;dataDir&gt;/build-cache/&lt;functionID&gt;/{npm,pip}`. Deliberately **not** under `functions/&lt;id&gt;/` — see §8; that tree is already orphaned on delete, so putting it there inherits an existing leak.
- Mount: a *third* bind, `-B &lt;cacheDir&gt;:/cache`, alongside the existing `-B &lt;scratch&gt;:/tmp`. Keep `HOME` throwaway. This is the design point — persisting all of HOME would persist npm logs, the update-notifier stamp, and anything a postinstall script drops in `~`. Persist exactly two cache trees and nothing else. Add a `BuildConfig.CacheDir` field; empty keeps today's behaviour (important for the unit tests in `buildjail_test.go`).
- Env: `npm_config_cache=/cache/npm`, `PIP_CACHE_DIR=/cache/pip`, `npm_config_logs_dir=/tmp/npm-logs` (npm's `logs-dir` defaults to `${cache}/_logs` and would otherwise accumulate in the persistent dir). Set these in the structural block of `buildJailArgs` and let them win over forwarded values.
- Bounds — three of them, none optional:
  1. `build_cache_max_age_days` (default 14) — sweep any per-function cache dir untouched for longer. Slots into the existing `GC.tick` in `builder/gc.go`, same `GetSystemConfigInt` pattern as `versions_to_keep`/`min_free_disk_mb` (`migrations.go:381-383`).
  2. `build_cache_max_mb` (default 2048) — global cap, evict whole per-function dirs LRU by mtime. Evicting a whole dir, never files within one, keeps both caches internally consistent.
  3. Explicit purge: `DELETE /api/v1/functions/{id}/build-cache` + `orva functions purge-cache`, and drop the dir when a function is deleted. Without this there is no clean recovery from a compromised build, which is the one property Option B gives up.
- Rough sizing: 15–46 MB per node function, ~38 MB per python function. 20 functions ≈ 1 GB — hence the cap.

**Restart / egress:** the data dir is a persistent volume and `scripts/entrypoint.sh` only refreshes the rootfs adapters (`entrypoint.sh:26-40`), so the cache survives restarts by construction — which is exactly why eviction is mandatory rather than nice-to-have. For nstun: a cache strictly *reduces* concurrent registry flows (npm's parallel tarball fetches are the bulk of them), so it moves away from the 1024 cap, never toward it. Neutral-to-helpful; not a factor in the decision.

## 7. What could still go wrong, and what I'd test

- **A cache that silently doesn't work.** Both installers fail soft on an unwritable cache dir — pip swallows the OSError outright. Assert cache reuse behaviourally: build twice, assert the second build's `build_logs` show no tarball fetches (or assert wall-clock), and assert `&lt;dataDir&gt;/build-cache/&lt;fn&gt;/npm/_cacache/content-v2` is non-empty. A test that only checks the flags were passed will pass while the feature is dead.
- **Cache dir permissions under `ORVA_DISABLE_USERNS=1`** — the existing scratch dir needs `0777` for exactly this reason (`build.go:139-143`); the cache dir needs the same treatment, and a bare-metal install is the case that catches it.
- **Eviction racing an in-flight build.** Take the function's `FnLock` before removing its cache dir, or skip dirs with a recent mtime.
- **Disk-cap interaction** with `min_free_disk_mb` (`builder.go:243-263`) — the pre-flight check should account for the cache, and eviction should be triggerable by low disk, not only by the timer.
- **Regression guard on isolation:** a test asserting the jail args contain exactly one cache bind, scoped to the building function's ID. That is the invariant that stops someone "simplifying" this into a shared dir in six months.

# Adversarial security review — PR #39 (`feat/remove-nftables-nstun`)

I ran a throwaway instance (port 19870, isolated data dir, killed and cleaned up — the user's `:3000` and an unrelated agent's `:19882` were left untouched) and drove nsjail directly with policy files the daemon actually produced. The migration is largely sound: build-jail escape attempts failed (EROFS/EACCES/ENOENT), per-function cache isolation holds, the spawn path is genuinely fail-closed (no policy → `ErrEgressPolicyMissing`), and `fnScopedPath`'s delete guards are solid. But the PR's **central, repeated safety claim** — *"every value is parsed with netip … unspecified addresses refused … so a malformed rule cannot become a wildcard"* — is **materially false for two of the three input paths** that feed addresses into the compiled policy. Both are reproducible and both are reachable by a non-admin `write`-scoped API key.

First, the nsjail fail-open the PR describes is real and I reproduced it: `dst_ip: "0.0.0.0/32"` matches **every** address, not just 0.0.0.0 (nsjail treats an all-zero dst as "unset = match-any", the /32 notwithstanding). The compiler's guard against this (`parseTarget`, `policy.go:338/343`) is applied **only to CIDR blocklist rules**. The DNS-server path and the hostname path never call it.

## Finding 1 — [Medium] Zero DNS-resolver compiles to a match-any ALLOW on port 53 (silent partial blocklist bypass)
- **Breaks:** "unspecified addresses refused… a corrupted ALLOW is allow-everything, with no log line" and "every value is validated here."
- **Where:** `backend/internal/firewall/manager.go:495-507` (`dnsServerAddrs`, no unspecified filter) → `backend/internal/firewall/policy.go:208-217` (DNS carve-out emits `hostPrefix(s)` with no `IsUnspecified` check). Accepted at the API by `handlers/firewall.go` `PutDNS` because `net.ParseIP("0.0.0.0") != nil`.
- **Reproducer:** `PUT /api/v1/firewall/dns {"servers":["0.0.0.0"]}` (200, works with a `read,write` key — no admin needed). The daemon compiles an `ALLOW … dst_ip "0.0.0.0/32" dport 53` rule that precedes all REJECTs. Enforcing that exact file:
  ```
  1.1.1.1:53  -&gt; CONNECT   (1.1.1.0/24 is in the blocklist)
  1.1.1.1:443 -&gt; REFUSED
  ```
  Every blocklisted destination becomes reachable on TCP/UDP 53 — a textbook DNS-exfil/C2 channel. `GET /firewall/status` reports `enforced: true`, lists a benign-looking `"0.0.0.0/32"`, and raises **no** `unenforced` entry. `::` does the same for IPv6.

## Finding 2 — [Medium] Hostname rule `0.0.0.0` compiles to a match-any REJECT (silent full egress DoS)
- **Breaks:** same claim; also "a malformed rule doesn't become stricter, it becomes a wildcard" — the PR says it prevents exactly this.
- **Where:** `backend/internal/firewall/policy.go:244-255` (hostname branch: no `IsUnspecified`/`Is4In6` guard). The API's hostname branch does no IP validation, and `net.LookupHost("0.0.0.0")` returns `["0.0.0.0"]`.
- **Reproducer:** `POST /api/v1/firewall/rules {"rule_type":"hostname","value":"0.0.0.0"}` (201, `write` key). Produces `REJECT … dst_ip "0.0.0.0/32"` proto ANY = match-any. Enforcing the daemon's file:
  ```
  8.8.8.8:443 -&gt; REFUSED
  93.184.216.34:80 -&gt; REFUSED   (everything blackholed)
  ```
  One request from a non-admin key silently severs **all** egress for every `network_mode=egress` function, while the dashboard shows the policy as healthily enforced — an operator will burn hours before suspecting their own rule.

Both findings share one root cause and one-line fix: route DNS-server addresses and hostname-resolved addresses through the same `IsUnspecified`/`Is4In6`/canonicalization gate `parseTarget` already applies to CIDRs (drop-and-report, don't emit).

## Finding 3 — [Low→Medium] Daemon-side exemption is broader than the sandbox carve-out ("cannot drift apart" is false)
- **Breaks:** `policy.go:437-440` / `manager.go` claim that `Policy.Blocks` "walks the same rules… the sandbox gets, so the daemon and sandboxes cannot drift apart."
- **Where:** the sandbox control-plane rule is **port-scoped** (`policy.go:201-204`, TCP `dport: cp.Port`), but the daemon's exempt set is the **bare address on all ports** (`manager.go:245` `exempt: m.cp.Addrs`; `policy.go:451-455` compares address only, ignores port), plus loopback is unconditionally exempt (`policy.go:448`).
- **Reproducer:** with `10.1.1.20/32` (the control-plane host) in the blocklist, a webhook delivery to `http://10.1.1.20:19871/` **succeeded (200)** from the daemon, while a sandbox to `10.1.1.20:19871` was **REFUSED**. So the operator's blocklist does not cover the daemon for *any* port on the control-plane host, nor for loopback. On single-node installs the control-plane address is the box's own LAN IP — precisely what an operator would want protected from SSRF-via-webhook. Webhook creation only needs `write`, so this is an SSRF hole for a non-admin key, not just admins. Fix: scope the daemon exemption to the SDK port (mirror the compiled carve-out) rather than exempting the whole address.

## Finding 4 — [Informational] `egressConfigArgs` stat is content-blind; a rules-less-but-parseable config runs unfiltered
- `sandbox.go:347` only `os.Stat`s the policy file. I confirmed that a config which parses but omits the `user_net` block, combined with the CLI `--user_net` (which is appended unconditionally for egress), starts nsjail and yields **fully unfiltered** egress. An *empty* file fails closed (nsjail rejects it), and Orva only ever writes complete files atomically, so this is **not reachable through Orva's own code** — but the "fail-closed" guarantee rests on that invariant, not on the stat. A cheap hardening: have the manager assert `countRuleBlocks(rendered) &gt; 0` (it already exists) and/or have `egressConfigArgs` reject a zero-length/no-`user_net` file. Not blocking.

### MEDIUM

**6. `EvictIdleBuildCaches` can delete another function's cache mid-build.** `buildcache.go:293` passes `nil` as the tryLock where the GC paths correctly pass `g.tryFnLock` (`gc.go:183,210`). **#2 — real window, honestly narrower than claimed.** `retirePool` (`pool/pool.go:429-449`) is decisive when it fires: pool removed from map, idle workers killed, busy killed on release — so no stale-generation checkout after retirement. **#3 — the MCP gap matters.** MCP is the in-product AI assistant's path. `delete_firewall_rule`'s own description asserts "recycles the warm egress workers, so traffic the rule was blocking is reachable again within seconds" — stated as fact while the error is dropped. *Fix:* route all three through the same `refreshEnforcement` helper.
