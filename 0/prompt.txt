# Orva Pool, KV, and Tracing Hardening Plan

## Summary

Deliver the work as three sequential PRs:

1. `codex/kv-sdk-reliability`
2. `codex/pool-controller-v2`
3. `codex/trace-diagnostics`

Each PR branches from the latest `main`, includes its own documentation and regression tests, and merges only after the consolidated CI and CodeQL are green. Rebase the next PR onto the newly merged `main`; delete merged branches afterward. Do not create a release tag or deploy production as part of this work.

## PR 1 — KV Reliability and Scoped SDK Identity

- Replace the process-wide bearer credential with a process-signed, function-scoped SDK token containing the immutable caller function ID and token version. Handlers derive caller identity from the verified claim and never trust `X-Orva-Caller-Function`.
- Apply scoped authentication consistently to KV, function invocation/streaming, jobs, cron upsert, and user-span endpoints.
  - KV requests may access only the credential’s function namespace.
  - Cron upsert may modify only the caller’s schedules.
  - Invokes and jobs may target other functions, but caller/trace attribution always comes from the credential.
  - User spans must reference an execution owned by the credential’s function.
  - Invalid, tampered, stale, or cross-function credentials return a standard 401/403 error.
- Enforce the documented KV contract on operator and SDK paths: non-empty UTF-8 key up to 256 characters, valid JSON value up to 64 KiB, at most 100 batch operations, and bounded request bodies.
- Make batches atomic. Validate every operation before opening the transaction; any validation or database failure rolls back every write. SDK `putMany`, `deleteMany`, and `getMany` throw when the batch fails instead of reporting partial success.
- Change TTL inputs to optional values:
  - omitted TTL preserves an existing expiry;
  - explicit `0` removes expiry;
  - positive TTL sets or refreshes expiry;
  - negative TTL is rejected.
  New keys with omitted TTL are persistent.
- Add context-aware KV database methods and cancel database waits when the function/request deadline expires.
- Replace async-writer overflow goroutines with bounded critical and telemetry queues. Critical writes return/backpressure on deadline; droppable telemetry records a metric when discarded. No unbounded goroutine fallback remains.
- Add KV operation, latency, timeout, batch rollback, writer queue-depth, and dropped-telemetry metrics. Health output reports writer saturation separately from read-database health.
- Update Node/Python SDK types, errors, TTL documentation, MCP reference, examples, and embedded adapter copies. Correct the cron/KV example’s egress requirement, entry iteration, and `next_cursor` usage.

## PR 2 — Pool Controller v2

- Remove `target_concurrency` immediately from the REST/MCP types, database model, metrics, documentation, and UI. Requests containing it return `400 VALIDATION` with a migration message.
- Rebuild `pool_config` idempotently without the removed column while preserving all other values and foreign keys.
- Normalize scale configuration:
  - `scale_to_zero=true` requires and migrates `min_warm=0`;
  - `scale_to_zero=false` requires `min_warm>=1`;
  - defaults remain min 1, max 50, idle TTL 600 seconds, scale-to-zero off.
- Record demand before any host or function concurrency wait. Track arrivals, busy, idle, queued, spawning, queue-wait duration, service duration, cold-start duration, rejections, and capacity timeouts per function.
- Use a single-flight worker capacity model with an internal 70% utilization target:
  - stable capacity derives from 60-second arrival rate × service P95;
  - burst capacity derives from 6-second arrival rate × `(service P95 + spawn P95)`;
  - immediate pressure includes busy plus queued work;
  - desired workers are the maximum of those signals, clamped by configured minimum and effective host maximum.
- Introduce one coordinator per pool. It may start up to four workers concurrently, but increments `spawning` before launch so repeated ticks cannot duplicate work.
- Scale down only idle workers after 30 seconds continuously below target, at no more than 20% per evaluation. Scale-to-zero occurs only after no arrivals, queued work, or busy workers for the configured idle TTL.
- Calculate effective capacity using cgroup v2 `memory.max`, `memory.current`, and CPU availability, falling back to `/proc/meminfo` only outside a constrained cgroup. Use observed worker memory P95 with the declared cgroup limit as the hard bound.
- Add a global round-robin spawn scheduler so active functions receive alternating admission opportunities. Under memory pressure, reclaim borrowed idle capacity from the largest pool before rejecting a queued function; never kill busy workers or violate configured active minimums.
- Keep operator `max_warm` as a hard per-function ceiling, but allocate internal worker storage from effective host capacity rather than directly from an untrusted maximum value.
- Replace obsolete metrics with queued, spawning, queue-wait, desired workers, limiting reason, cold-start P95, service P95, and effective memory/CPU capacity.
- Rewrite capacity documentation from measured validation results and remove stale statements about lazy spawns and memory reservation.

## PR 3 — Trace Correctness and Developer UX

- Define a local trace root as the earliest span whose parent is absent from the same trace. This keeps externally parented W3C traces visible while preserving the external parent ID.
- Aggregate trace-list status, duration, outlier state, span count, error count, and cold-start count across all spans:
  - any failed span makes the trace status `error`;
  - duration is earliest start through latest finish;
  - function filtering matches any span and accepts exact function ID or name.
- Add composite trace indexes and use a stable `(started_at, trace_id)` cursor. Emit an opaque cursor while temporarily accepting legacy timestamp cursors.
- Preserve existing summary field names but change their documented semantics to trace-wide values. Add `span_count`, `error_count`, `cold_start_count`, and `external_parent_span_id`.
- Replace the duplicate waterfall/table layout with one causal, expandable waterfall:
  - indent spans from `parent_span_id`;
  - label invoke, job, cron, replay, and external-parent relationships;
  - show status code, cold/warm state, error summary, duration versus baseline, and linked logs in the expanded row;
  - select a span without leaving the trace page, with an explicit secondary action to open its invocation;
  - provide all-log/selected-span views and expandable structured fields.
- Add useful time presets and retain function/status/outlier filters. Keep information density compact and avoid introducing additional cards.
- Make rows real buttons or keyboard-operable controls with visible focus, Enter/Space activation, semantic section headings, accessible status text, and at least 44×44 px touch actions.
